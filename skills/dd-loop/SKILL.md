# DD Loop — 8 步開發迴圈的做法細則

全域 CLAUDE.md §3.9 列出 8 步與不能跳的關卡；這份寫各步怎麼做。兩邊講法不同時，以全域 §3.9 的關卡為準。

## 段落起點與 `<起點>`

段落開始前先跑 `~/.claude/scripts/check-claude-md.sh --start-segment`，印出「段落起點：…」才算記好。
⚠️ **這個指令有兩個擋點**：①起點以來有 `SKIP_DOC_CHECK=1` 欠下、還沒補的 CLAUDE.md
②**專案有 `docs/reviews/` 目錄時**（= 採用了 review 留痕慣例），上一段的 commit 範圍內
沒有新增 `docs/reviews/S*.md`。兩者都會 `exit 1` 並印出該怎麼做 —— 照它印的做，不要繞過。
剛採用第二個慣例、而且上一段的起點檔存在又不是空樹時，第一次會被擋（上一段本來就沒報告；從沒記過起點、或上一段從空樹開始的專案不會被擋）。
出路是補一份 `docs/reviews/S<上一段>-SKIP.md`（沒有段落編號就用 `S1`，理由寫「採用 review 留痕之前的段落」）並**連同 trailer 一起 commit** —— 只建檔不 commit 還是會被擋。
印的是「迴圈暫停中」（使用者用 `/dd-stop on` 暫停了這個專案；這時 exit 0）也算沒記好，但不用修：照它印的只做步驟 1、2（commit 照平常下，不加 `SKIP_DOC_CHECK=1`），不跑步驟 3–8，不要為了記起點去清旗標，
回報時講一句這個工作因為暫停沒跑步驟 3–8；恢復由使用者下 `/dd-stop off`，恢復之後再跑 `--start-segment` 時照常查（暫停期間欠的 CLAUDE.md 沒補完會被擋）。
其他沒印出「段落起點：…」的情況就是沒記好。舊版 gate 的徵兆是**什麼都不印、exit 0**（沒有 staged 時）或印「commit 已擋下」（有 staged 時）；
用 `grep -q -- --start-segment ~/.claude/scripts/check-claude-md.sh || echo 舊版` 確認（少了 `--` 會被當成 grep 的選項）。
是舊版就不要照它印的補檔或 commit：到本機的 claude-dd clone（沒有就 `git clone https://github.com/kopp0510/claude-dd`）跑 `git pull && ./install-dd-pipeline.sh --force`，再重跑一次 `--start-segment`。
一段常有好幾個 commit,
步驟 3、4、8 都要看「起點到現在」的整段,下文的 `<起點>` = `~/.claude/scripts/check-claude-md.sh --segment-base`
的輸出(exit 非 0 或輸出是空的 = 範圍沒算出來,不是範圍為空)。只看最後一個 commit 會漏(實測)。
**`--segment-base` exit 非 0 時,不要順手重跑 `--start-segment`**:起點會移到現在的 HEAD,這一段已經 commit 的就全部不在範圍裡(`git diff <起點>` 變成 0 行,實測)。
有進度表 → 用表上這段的起點(見下方)。沒有進度表 → 看它印在 stderr 的那一句:
「沒記過」→ 範圍不明,問使用者這一段從哪個 commit 開始;
印出「共同祖先是 `<sha>`」(起點被 amend、rebase 掉,或換過分支)→ `<起點>` 用那個 sha,不用問:目前分支上這一段的 commit 不會漏,只會多審;
「找不到共同祖先」或「內容不是 commit」→ 問使用者;
這幾句都沒有(錯誤印在 stdout:`dd.docfile` 不合法、不在 git repo 內)→ 照它印的先修好,再重跑 `--segment-base`。
問到或取到起點之後,這一段剩下的步驟(3、4、8)都用同一個值,不要中途改回 `--segment-base`。
忘了記下一段的起點時,範圍會連上一段一起算 —— **SKIP 欠下、還沒補的 CLAUDE.md 只會多審,不會漏;
但「上一段有沒有附 review 報告」那個檢查會漏一整段**(上一段的報告會把這一段的要求頂掉,見下方「報告一律落地」那條)。
**但這只在「起點檔已經存在」時成立**:從來沒跑過 `--start-segment` 的專案(例如剛照 UPGRADING 改用段落起點的舊專案),
要等第一個 `SKIP_DOC_CHECK=1` commit 才會自動補記,起點就落在段落中間,它前面的 commit 步驟 3、4、8 全部看不到。
這時 gate 印的是「記下段落起點 …」、`--segment-base` 也正常 exit 0,兩個訊號都看不出範圍已經縮水。所以段落開始前一定要自己跑一次。
**有進度表時 `--segment-base` 不是最終答案**:專案有 `task-planner` 產的進度表
(`docs/designs/…` 的「進度表」)時,`<起點>` 以**表上這段 commits 欄的起點**為準,**只取 `..` 前面那段**(`4b71e3b..` 填 `4b71e3b`)。
連 `..` 一起代入會靜靜出錯:`git diff 4b71e3b..` 等於 `4b71e3b..HEAD`,漏掉工作目錄還沒 commit 的改動且 exit 0;
`git diff 4b71e3b.. HEAD` 回 exit 129,放在管線裡整條仍 exit 0。
兩者在「回頭做 `BLOCKED` 過的段落」時會不一樣 —— 中間插做別段會把 `--segment-base` 往後推,
用它就漏掉這段先前已經寫好的部分;表上那個較舊、較寬,只會多審。
**半號段落**(`S2.5` 這種插在兩段之間的 hotfix)有自己的 commit 且改了人工邏輯 → 算新段落,要走步驟 3–8;
只是把前一段漏掉的檔案補進同一個 commit、或純文件/資料改動,才算前一段的小任務(只走 1、2)。不管有沒有進度表、用哪種 task 工具都一樣

## 步驟 3、4：code-simplifier 與 code-review

步驟 3 跑 code-simplifier 時只針對該段新增/修改的程式碼:`git diff <起點>`。步驟 4 每段全量跑,修掉 Critical/Important 級發現才續行;細則:

- 範圍要明講:依序跑時 `git diff <起點>` 加上 `git ls-files --others --exclude-standard`(步驟 3 新增、
  還沒 commit 的檔案 `git diff` 看不到),並行時 `git diff <起點> HEAD`。沒講的話,本地 code-reviewer agent
  預設只看還沒 staged 的 `git diff`,已 commit 的整段都審不到
- **這一段沒有「人工寫的程式碼」就不要派 agent**:diff 全是資料、設定、註解或文件,
  或改動已被專案的機械檢查完全覆蓋(渲染等價比對、round-trip 檢查這類)時,改成自己逐條核對、
  在回報附證據(可用 `verification-gate` skill),並在設計文件「段落與小任務」該段底下寫明跳過的理由(沒有設計文件就寫在回報裡);
  有 `docs/reviews/` 時另建 `S<段落>-SKIP.md`(位置與寫法見下方「報告一律落地」那條)。
  判準是**「這段有沒有正確性還沒被機械檢查證明的人工判斷」,不是 diff 多長**。
- ⚠️ **派工的 prompt 交事實(行號、數字、實測輸出),不要交「我判斷元凶是 X」** ——
  自己的錯誤診斷寫進去,reviewer 會跟著錯。要寫就標明是推測。
- **派工前先準備一個 diff 檔**(放 scratchpad),內容:①「範圍要明講」那條算出的整段 diff;
  ②步驟 3 自己改了什麼(依序跑時 `git diff HEAD`,simplifier 新增的檔它看不到,另用 `git ls-files --others --exclude-standard` 列出來標明是步驟 3 加的;分開附 —— simplifier 改了行為正是要抓的,
  混在整段裡審查者看不出是誰改的);③**派工當下**被改到檔案的整檔內容(依序跑時取工作目錄版本,
  就是 diff 描述的那一版,另把未追蹤的新檔放整檔;與步驟 3 並行時取 `HEAD` 版本,因為 simplifier 正在改工作目錄);
  ④步驟 1(重跑時加步驟 5)已經跑過的驗證輸出,**連同預期值一起寫**,派工 prompt 標明這些已確認、不要重跑(不寫的話它會把測試、build、渲染指令整組再跑一遍)——「跑過」不代表結果對(實測)。
  被改到的檔,審查者與主對話一律讀 diff 檔裡那一份、不讀工作目錄;沒被改到的檔照常讀。
- **diff 檔用 Read 的 `offset`/`limit` 每次 300 行讀到最後一行**,這句也寫進給審查者的 prompt:
  Read 一次讀太多會**靜靜截斷、不報錯**(約 47 KB 就停;實測 3024 行的 diff 檔只回 544 行)
- **主對話直接派審查者**:用 Agent 工具**在同一則訊息裡平行**派審查者
  (`subagent_type: "code-reviewer"`;其中**剛好 1 個**帶 `model: "opus"`,負責 diff 裡最需要推理的部分(測試與它要測的程式、斷言證明了什麼),其餘不帶 model 參數、用 agent 定義的 sonnet,不換 haiku;全 sonnet 時實測漏掉「測試證明不了它宣稱的事」那類錯,`docs/measurements/2026-11-26-sonnet-reviewer.md`)**最少 3 個**,
  數量是設定的下限,實際數量自己定,理由寫進 `-judge.md` 的「派工」節。**先派工、派完自己讀 diff 檔**(跟審查者同時進行)。
  一發只會挖到一部分（實測每發命中的已知錯誤子集不同），所以要好幾發。派工 prompt 寫明審查者的職責:找漏洞、每條附證據、沒證據不算。diff 動到併發或資料庫鎖、「擋誤用」或「讓 X 可偵測」的機制、git 進行中狀態、測試的鑑別力、識別符(函式名、欄位名、設定鍵)或清單的分母,以及驗證結果是 0 紅或無輸出時(全域 §3.9「規則」那一條列的同一組),派工 prompt 另寫一句「審之前先用 Read 讀 `~/.claude/skills/dd-loop/lessons.md` 整份,照對應的那一條判」(審查者是 sonnet,只靠全域 CLAUDE.md 的指路句實測 0／3 會去讀,`docs/measurements/2026-11-26-lessons-pointer.md`)。
  某個審查者失敗、沒回來或報告不完整 → 補派,補不了就照實寫進報告(哪個、為什麼),不能當作它沒有發現;
  收回的完整報告少於 3 份 → 不算跑過步驟 4,照實說,不續行
- 不另派裁決者：2026-10-24 實測主對話直接派命中 4/6，另派裁決者 3/6（n 小、只是方向）
- **等全部審查者回來才查證**:派工 prompt 派出時、每個審查者的完整報告(含 Not reported、What I ran)一回來,
  都逐字存進 scratchpad 檔(之後照它落地成報告;context 被壓縮後也還在)。逐條讀程式碼查證(預設「這條可能是錯的」),分三類:採納 / 駁回 / 需使用者決定。
  採納的項目沿用審查者標的級別,調級要寫理由;採納的 Critical / Important 修掉才續行,
  Smells 採納了照改、不擋。審查者列的外部查證項,能查就查,查不了另列「需要外部查證」。
  ⚠️ 查證的人就是寫這段 diff 的人 —— 「預設這條可能是錯的」反過來也要用在自己的辯護上:要駁回就讀程式碼證明,不憑記憶
- 派工 prompt 寫明「只用手上的資料判斷,需要外部查證的列出來交回」;不設審查者的工具次數上限(砍上限會連查證一起砍)。
- **審查者對同一處講不一樣時,讀程式碼判定,不表決**。被判成「既有問題、不是這次 diff 引入的」項目,
  要回去看那幾行:這次 diff 可能把同一個錯誤寫法複製進了新的程式碼路徑
- 發現若是「行為變了,但**無從判定哪個才是預期**」(程式碼、測試、文件都沒寫明語意),
  **用 AskUserQuestion 把選擇交回使用者**,不要自己選一邊也不要讓 reviewer 選 ——
  查證時把它標成「需使用者決定」(附選項與建議答案)再問。
  金額、權限、資料保留期這類決定選錯了不會報錯,只會靜靜地錯下去
- ⚠️ **報告一律落地成 committed 檔,跳過要申報。** 步驟 4 跑完不留任何痕跡、又最貴,是最容易被靜默跳過的一步;
  跳過也不會報錯,而步驟 7 要固化的教訓就來自它的發現。
  - 每個審查者一份 `docs/reviews/S<段落>-a.md`、`-b.md`、`-c.md`…,加一份查證 `S<段落>-judge.md`
    (檔名是歷史沿用,內容是主對話的查證);各三節:**派工 / 發現 / 處置**。
    審查者那幾份:「派工」照給它的派工 prompt 寫、「發現」放 scratchpad 裡的逐字原文、「處置」寫怎麼處理;
    審查者之間的重疊項與獨有項寫進 `-judge.md`。
    **專案還沒有 `docs/reviews/` 目錄時,第一次落地就建它** —— 目錄一建就等於採用留痕慣例,之後 `--start-segment` 會查上一段有沒有新增報告
    (剛採用時的出路見上方「段落起點與 `<起點>`」那段的 `S<上一段>-SKIP.md`)。
    `<段落>` 用進度表上的段落 ID;**沒有進度表時用 `S1`**,報告放子目錄 `docs/reviews/<日期>-<主題>/`(不放根目錄,免得不同工作的 `S1` 互相覆蓋)。
    **多張進度表時放子目錄** `docs/reviews/<進度表檔名去掉 -design.md>/`(段落 ID 會跨表重複)。不管哪一種子目錄,gate 都認得裡面的 `S*.md`。**寫之前先 `ls`**,
    因為覆蓋掉別人的報告時 `git status` 顯示的是 `M` 而不是 `??`,沒有任何警告。
    專案的 `docs/reviews/` 底下有自己的記憶檔(`CLAUDE.md`,或 `dd.docfile` 設的檔名)寫了別的命名慣例時,照它。
  - 跳過時建 `S<段落>-SKIP.md` 寫明理由,位置同上面的報告(沒有進度表時放 `docs/reviews/<日期>-<主題>/`、多張進度表時放該表的子目錄;寫之前先 `ls`,蓋掉既有的申報檔 gate 不算新增)(有 `docs/reviews/` 時 gate 的 `--start-segment` 要範圍裡新增一份
    `S<數字>…md`,只加 trailer 開下一段時會被擋),commit 訊息加 trailer `SKIP-REVIEW: <段落> <理由>`(放在 `Co-Authored-By` 那一段裡、緊接在它前一行,**中間不能空行** —— 隔了空行 git 就不認它是 trailer,下面的查法回空值、commit 照樣成功),
    同時寫進設計文件該段底下(沒有設計文件就寫在回報裡)。查的時候用
    `git log --format='%h %(trailers:key=SKIP-REVIEW,valueonly)'`,**不要用 `--grep`**
    (描述這條規則的 commit 自己就會命中)。
  - 這一段還沒做完、要先停下來做別段(進度表標 `BLOCKED`)時,建申報檔 `S<段落>-BLOCKED.md` 並 commit:寫明停在哪個小任務、為什麼停、先停之前已經 commit 的範圍;
    位置同上面的報告(多張進度表時放這張表自己的子目錄,寫之前先 `ls`);同一段第二次先停另建 `S<段落>-BLOCKED-2.md`;不用 trailer。**它只是申報,不算審查報告**:有它 `--start-segment` 才讓你開別段,
    回頭做完這一段時步驟 4 照跑、報告照上面的格式落地。
  - ⚠️ 報告驗不出真偽,只是拿掉「靜默省略」。`.md` 不在 gate 的 `CODE_EXT` 裡,pre-commit 不強制它存在
    (只在開下一段時查「有沒有新增任何一份」)—— 不要把它寫成閉環。
  - ⚠️ **證據不可以放 `.git/` 底下**(段落起點檔每個 worktree 各一份、不進版控)。
- ⚠️ **「程式碼只有一行 / 輸入定義域全被測試覆蓋」不是合法的跳過理由**:review 抓的是
  **註解與文件裡的宣稱**,端到端的驗證看不到那一類東西。
  ⚠️ **判準用「有沒有引別處」而不是「程式碼幾行」**:diff 裡只要有
  「引別處行號 / 函式 / UI 字串 / commit 範圍」的敘述,就不能拿「只有一個運算式」當跳過理由。
  **hotfix 性質的段落通常正是人工判斷最密的地方。**

## 步驟 8：先算範圍

下面這段是**沒有進度表**時的寫法;**有進度表時 `base` 改填表上這段 commits 欄的起點**(只取 `..` 前面那段,見上方「段落起點與 `<起點>`」;
連 `..` 一起填時第一條 `git diff` 回 exit 129,整條管線卻 exit 0,只列出還沒 commit 的那幾份,看起來就像範圍正常):

```bash
f=$(git config --local --get dd.docfile); [ -n "$f" ] || f=CLAUDE.md
base=$(~/.claude/scripts/check-claude-md.sh --segment-base) && [ -n "$base" ] &&
{ git -c core.quotePath=false diff --name-only "$base" HEAD
  git -c core.quotePath=false diff --name-only HEAD
  git -c core.quotePath=false ls-files --others --exclude-standard; } \
  | while IFS= read -r p; do [ "${p##*/}" = "$f" ] && printf '%s\n' "$p"; done | sort -u
```

第一行取記憶檔名：專案設了 `git config --local dd.docfile`（例如 `AGENTS.md`）就用它，沒設或設成空字串就是 `CLAUDE.md`，跟 gate 的讀法一樣（只讀 `--local`）。
比對的是路徑最後一段**整個等於**那個檔名，不把檔名放進正規式（`.` 會變成萬用字元）。

後兩條是「還沒 commit 的」(已追蹤的改動 + 未追蹤的新檔;步驟 7 剛寫的、被 gate 逼著補的 CLAUDE.md 正是這個狀態)。
**不要改用 `status --porcelain -uall | awk '{print $NF}'`**:含空白的路徑會被加引號、從空白切開,少列一份卻照樣 exit 0。

算出幾份就只審那幾份,用 `claude-md-management:claude-md-improver`。
**記憶檔名不是 `CLAUDE.md` 時(設了 `dd.docfile`)不要用它**:它的 Phase 1 只 `find` 名叫 `CLAUDE.md`、`.claude.md`、`.claude.local.md` 的檔,在那種專案找不到記憶檔;改成自己逐份審算出來的那幾份,判準照全域 §3.10。
**該 skill 的 Phase 1 是「find 全部」,不先算範圍就會全 repo 掃**,產出跟本輪無關的長報告。範圍算出來是空的才跳過這一步(指令 exit 非 0 是範圍沒算出來,不算空:照上方「段落起點與 `<起點>`」那段取到起點,把 `base=` 那一段換成 `base=<那個值>` 再跑)

## 步驟 7、8 的關係

- 步驟 7 處理「本輪學到什麼」,與全域 §3.9「功能落地後,受影響目錄的巢狀 CLAUDE.md 逐層堆疊更新」那條(程式碼改了所以文件要同步)是兩件事
- **步驟 7 跳過不代表步驟 8 也跳過**:步驟 2、6 commit 時 pre-commit gate 會逼著更新
  改碼目錄的 CLAUDE.md,那些改動不是步驟 7 加的,但一樣要審 — gate 只確認「有寫」、
  **不確認「寫得對」**,這一格正是步驟 8 存在的理由
- **順序不可反**:7 是加、8 是整理。反過來的話 8 剛整理完 7 又塞新東西進去,白做
- **步驟 8 的發現分兩類,不要把選擇丟回給使用者**(使用者未必知道該修什麼):
  實跑驗證得出來的錯(指令、檔名、數量、路徑與實際不符)→ **直接修,不問**,結尾報一行;
  主觀建議(太囉嗦、結構可更好)→ **提一次就好,不動手**。判準是「能不能實跑驗證」
- **步驟 7、8 動到檔案就要 commit**:`.md` 不在 gate 的程式碼副檔名清單裡,不會被擋,
  但留著未提交的改動會混進下一輪
