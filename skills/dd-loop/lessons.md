# 驗證教訓（全域 CLAUDE.md §3.9「規則」的延伸）

2026-11-26 從全域 CLAUDE.md（`templates/global/CLAUDE.md`）§3.9「規則」原文搬來，內容沒有改。
迴圈外的修改、迴圈暫停中也一樣適用。同目錄的 `writing.md` 是全域 §3.10 寫文件的判準。

- ⚠️ **要擋 read-then-write 的 race,「包進交易」通常是錯的修法 —— 先查隔離級別。**
  在 `read committed`(Postgres 預設)下**交易只保證原子性,不保證「我讀到的 pre-image
  到我寫入時還沒變」** —— 兩個交易讀到同一份 pre-image、各寫自己那一欄,照樣落成要擋的狀態。
  **要先取鎖再讀**:`SELECT … FOR UPDATE` 可以,**但它鎖不住不存在的列**
  (「首次建立」那條路完全沒有序列化,而 upsert 的 `ON CONFLICT DO UPDATE` 會安靜地蓋上去)。
  **列可能不存在時用 advisory lock**,兩者都不需要 migration。
  ⚠️ 另一個前提要自己 grep:**那張表的寫入端只有這一處嗎** —— 多一個繞過它的寫入路徑,
  這道鎖就只保護一半。
- ⚠️ **併發 bug 不要用「同時打兩發」來驗 —— 窗通常是次毫秒級,打不到**(裸打十幾輪可以完全沒踩到)。
  **做法是可控實驗**:在讀與寫之間**臨時插一個 sleep 把窗拉寬**,修前 / 修後各跑一次,
  驗完拆掉並確認 `grep` 回 0、程式碼與實驗前逐字相同。
  ⚠️ **而且要先確認「資料集真的能觸發」** —— 否則被擋下的可能是那支自己的輸入驗證、跟鎖無關,
  而那個錯誤碼會被讀成「鎖生效了」。**資料設錯 + 結果讀錯,疊起來剛好長得像成功。**
- ⚠️ **寫一個「擋誤用」或「讓 X 可偵測」的機制之前,先驗三件事**(實測三項各自獨立出錯):
  ①**誤用發生的那一刻,這個機制存在嗎** —— 只存在某個 branch 的檔案,切到別的 branch 就從
  工作目錄消失,它檔頭描述的情境**永遠到不了它**(實證:一支只在 `company` branch 的 wrapper,
  宣稱要擋「在 `main` 上誤跑部署」,而 `git show main:<該檔>` 根本不存在)。
  ②**稽核的基準不可以取自被稽核的對象** —— 記「目標檔**現在**的 sha」只能證明「從記錄那刻起
  沒變」,不能證明「記錄那刻是對的」;先被污染過就會回報「一致」。基準要取自**來源**,
  或改成**自動的事後斷言**(不依賴人記得手動比對)。
  ③**只在部分參數下才成立的後置動作,用參數白名單擋,不要靠 exit code** —— 被包的指令在
  `--check` / `--help` 這類參數下 exit 0 但什麼都沒做,照 exit code 往下走就會把
  「什麼都沒做」蓋章成「做成功了」。
  ⚠️ 而**先 grep 既有的痕跡有沒有更強的**:曾有一次新造的雜湊記錄,被既有的
  「覆蓋前備份整份內容並印出路徑」完全蓋過 —— 新機制只該補既有痕跡**真正缺的那一格**。
- ⚠️ **驗 git「進行中」狀態(rebase / merge / cherry-pick)不可以手動造 `.git` 內部目錄。**
  真實 rebase 衝突時 HEAD 是 **detached**,`git rev-parse --abbrev-ref HEAD` 回 `HEAD` ——
  所以任何「先比對 branch 名」的檢查都會先命中,後面那段 rebase 判斷**永遠不可達**。
  而「branch 還掛著 + `rebase-merge` 目錄存在」這個組合**現實中不存在**,手動 `mkdir` 造出來
  測到的是假綠(實測)。做法:用真的 `git rebase` / `git merge` 製造衝突。
- **鑑別力測試(改回舊版確認會紅)的判定式要比對「固定版的完整輸出」,不要斷言某個預期的壞結果**:
  實測 —— 變異版掉進**第三種**狀態(我預期它停在 A、實際變成 C),判定式於是回報
  「變異沒被抓到」,而**測試其實有鑑別力**。
  寫法:先記下固定版的輸出字串,變異版只要「不等於它」就算紅。
  ⚠️ 但「不等於」要來自被測的東西給了錯的結果:變異讓檔案載入不了、import 壞掉、測試資料建不起來也會「不等於」,那不算(§3.5)。
  ⚠️ 而「有牙」只證明**我的碼與舊碼在這一格不同**:不證明新的那一邊**該**發生
  (去另一側 —— 後端 / 資料庫 / 呼叫端 —— 確認那個行為是不是真的該發生),
  也不證明**清單是全的**(缺陷有「類別」時,另外跑一次全站同類掃描)。
- ⚠️ **「0 紅 / 沒有差異 / 無輸出」的第一個嫌疑人永遠是實驗本身**,依序自檢再談鑑別力:
  ①**變異真的生效了嗎**(`grep -c` 那個字串或印一個標記)②**總數對得上嗎**
  (suite 數與測試總數 —— 載入失敗時「綠色數字變小」長得像成功)③**實驗到達那個狀態了嗎**(印中間狀態)。
  而「紅數」本身不是證據:它同時綁「斷言集合」與「變異的具體寫法」兩個會變的東西,
  **要記「哪個變異 → 哪幾個情境變紅」。** `2>/dev/null` 只在「已知那個錯誤長什麼樣且不在意」時才可加。
- ⚠️ **diff 動到的每一個識別符各跑一次 `git grep`,逐條核「這句話在 HEAD 還成立嗎」。**
  要找的不是「同型的兄弟」,是**誰提到這個符號的性質** —— 吃這個值的呼叫端型別檢查找得到,
  而「引用它存在 / 它的語意」的那些敘述沒有任何機械檢查看得到,它們就在同一個檔往下幾行到上百行。
  ⚠️ 一句含**兩個**宣稱的註解會被「修一半」(每一輪只看自己那段 diff),兩個都要重新判;
  同一個檔的檔頭與函式說明也可以互相矛盾,而讀的人不會預期要交叉比對。
  ⚠️ 查「誰在用它」時除了 grep 函式名,**還要 grep 它回傳的欄位名被誰讀** ——
  一個 `where` 不過濾的查詢,照樣可以靠 payload 的欄位讓前端畫出「不可用」。
- **清點一個清單時,先問「誰有資格進入分母」,再問「分母對不對」** —— 分母本身是對的、
  而排除條款吃掉了一整個檔,這種錯所有檢查都會放過。四條做法:
  ①**排除 / 篩選樣式錨定完整識別符或路徑**,不要用裸子字串;寫完**把已知的目標餵進去看它活不活得下來**
  ②**分母要含「元件自己那一份」** —— 抽共用元件時,被取代的那個原始手刻處自己也是一個呼叫點,回歸常落在那裡
  ③**從「誰在做決定」反推,不從「誰呼叫我改的那支」正推**:「我加了一個能力」≠「用得到它的地方都接上了」;
  要全就先列出所有「終點」(外送點 / 寫入點),再問哪些入口到得了
  ④**縮小範圍時把原始清單整份列出來逐項標「做 / 不做(理由)」**,不要從「我量到的」往回推範圍。
  ⚠️ 用「名字」當判準的規則**只對你已經想到的名字生效**;屬性/樣式的回歸要比對完整字串,不要 `includes` 片段。
