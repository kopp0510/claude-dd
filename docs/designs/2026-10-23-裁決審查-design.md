## 問題描述

- **計畫沒人挑**：複雜任務的計畫、task-planner 的段落草稿、design-brainstorm 的設計，現在都直接交使用者批。
  使用者要的是先經過一輪對抗式審查，自己只看結果
- **code-review 太慢**：實測真實 session 的 code-reviewer 一半約 12 分鐘以上、最慢一成約 28 分鐘以上；
  耗時跟工具次數走，工具呼叫的大宗是 git 類（`git diff/show/log`）—— 但慢的審查每一類工具都多好幾倍，「先交 diff 能加速」是推論，S4 才驗（`docs/measurements/2026-10-23-reviewer-real-sessions.md`，引用數字前照該檔重跑）
- **判斷審查意見的是作者自己**：現行步驟 4 由主對話（寫這段程式碼的那一方）判斷 reviewer 意見對不對

## 設計決策

| 決策 | 選擇 | 理由 |
|---|---|---|
| 裁決者怎麼開 | 主對話派出的 subagent（`general-purpose`） | 腦袋全新、看不到主對話；不需要 `claude -p` 的權限清單與開機時間。2026-10-23 實測 subagent 能再派 subagent 並拿到結果（`NESTED_OK`） |
| 裁決者模型 | Opus（派工時明寫 `model: "opus"`） | 它負責判斷哪些批評有效、正確、中肯 |
| 計畫審查者模型 | haiku | 便宜、快，負責猛攻；講錯的由裁決者刪掉 |
| code-review 審查者模型 | Opus（維持現狀） | 裁決者只能刪掉錯的意見，**補不回漏掉的錯**；程式碼漏錯會直接進 commit |
| 審查者數量 | 裁決者自己決定，**最少 3 個、不設上限**，報告寫明派了幾個與理由 | 使用者決定。可讓不同審查者專攻不同方向 |
| 審查者的職責 | 唯一職責是找漏洞、猛烈批評、證明原物有重大缺失；每條附證據（檔案行、grep 結果），沒證據的不算 | 使用者決定。不要客套、不要「整體不錯」 |
| 審查者之間 | 平行、互相看不到 | 使用者決定 |
| 裁決方式 | 對每條批評做對抗驗證（預設「這條可能是錯的」），自己讀檔判定、不表決，分「採納 / 駁回 / 需使用者決定」 | 沿用 §3.9「兩份報告不一致時讀程式碼判定，不要表決」 |
| 什麼要問使用者 | **只有**「程式碼、測試、文件都沒寫明該怎樣」的語意問題；其餘裁決者自己判 | 使用者先說不用問、後確認這類要問。裁決者是 subagent 不能直接問，寫進報告由主對話用 AskUserQuestion 問 |
| 什麼算重大 | 三個都符合：常走的路、照做會壞／錯／跳過使用者決定、錯了不報錯且後面關卡抓不到；其他算小事，照改但不擋通過 | 使用者決定（2026-10-24）。S2 計畫審了四輪，重大 5→2→2→2，後幾輪抓的都是邊角路徑 —— 舊定義「會漏」太寬，永遠等不到通過 |
| 計畫審查的通過條件 | 採納的意見全是無關緊要的小事 ⇒ 計畫已經夠好 | 使用者定義。但裁決者宣布通過前要確認每個審查者真的有讀檔（批評附了檔案行 / grep）；沒讀檔只挑得出小毛病，那種「沒問題」不算 |
| 迭代 | 主對話照採納的意見改 → 再送裁決者，最多 3 輪；到上限還有缺失就列給使用者並停下 | 防止無限繞圈 |
| 審查通過之後 | **直接開工，不再拿給使用者批**；開工前貼出最終計畫與駁回清單，使用者隨時可喊停 | 使用者決定。⚠️ 例外見下一列 |
| plan mode 的批准 | 在 plan mode 裡做的計畫（design-brainstorm、使用者開的 plan mode）**仍需使用者按一次 `ExitPlanMode`** | `ExitPlanMode` 是 harness 層的使用者批准，模型拿不掉（本次設計討論中被拒過一次）。能拿掉的只有模型自己問的批准題（例如 task-planner 步驟 4 的 AskUserQuestion） |
| code-review 拿掉裁決者（2026-10-24 S6，取代上面幾列裡 code-review 的裁決者結構；計畫審查不變） | 主對話直接平行派 ≥3 個 `code-reviewer`、派完自己分段讀 diff 檔、全部回來後自己逐條查證 | 使用者看完 S5 選「改成 A」：A 269s／US$5.13／命中 4，裁決結構 350s／US$3.83／命中 3（n=2/段；A 同時改了拿掉裁決者、分段讀、派工順序三件事，分不開）。下面「技術設計」畫的 code-review 流程是 S3 版本，已被取代 |
| code-review 加速 | 主對話派工前把整段 diff 存成一個檔交給審查者；grep 與讀前後文不限制；需要外部查證的列出來交回 | 使用者決定不設硬性工具上限（砍上限會連查證一起砍）。diff 檔是派工當下的快照，也順帶解掉「simplifier 正在改工作目錄」的問題 |

## 技術設計

### 計畫審查（新 skill `plan-review`）

```
主對話寫好計畫
  │ 交出：計畫全文 + 已查到的事實（讀過哪些檔、實跑輸出）；交事實，不交「我判斷 X」
  ▼
裁決者（Opus）
  │ 平行派審查者（haiku），最少 3 個，數量與理由寫進報告
  │ 審查者：唯讀；查前提成不成立、漏掉的「同時改」、範圍、驗證抓不抓得到錯
  ▼ 全部回來才開始判（2026-10-23 第一次巢狀測試，中間那層沒等結果就先交報告）
裁決者逐條對抗驗證 → 採納 / 駁回 / 需使用者決定
  ▼
有站得住的重大缺失 → 主對話改 → 再審（最多 3 輪）
都是小事 → 主對話問「需使用者決定」的題 → 貼出計畫與駁回清單 → 開工
裁決者失敗或沒回來 → 照實說「計畫審查沒跑成」，不靜默跳過
```

插入點（三處，都把「等使用者批准」換成「審查通過」，plan mode 的 `ExitPlanMode` 例外）：

- `templates/global/CLAUDE.md` §4.1：表格「複雜」那列，與「N ≥ 2 就呼叫 `task-planner`,由它拆段落、出計畫給使用者批准」那句
- `skills/task-planner/SKILL.md` 步驟 4「給使用者批准」與其完成條件
- `skills/design-brainstorm/SKILL.md` 硬閘門與步驟 8

### code-review（§3.9 步驟 4）

```
主對話
  │ ① 整段 diff + 被改到檔案的 HEAD 版本 → scratchpad 裡一個檔
  │ ② 已跑過的測試輸出（「已確認，不要重跑」）
  ▼
裁決者（Opus）
  │ 平行派審查者（Opus，subagent_type code-reviewer），最少 3 個
  ▼ 全部回來
裁決者逐條讀程式碼查證 → 採納 / 駁回 / 需使用者決定
  ▼
主對話修 Critical/Important → 寫報告 → 步驟 5 再測
```

報告：`docs/reviews/S<段落>-a.md`、`-b.md`、`-c.md`…（每個審查者一份）＋ `S<段落>-judge.md`（裁決）。
gate 的樣式 `(^|/)S[0-9][^/]*\.md$`（`scripts/check-claude-md.sh` 的 `reviews_missing`）已經認得這兩種檔名，判定不用改；
寫死「-a.md 與 -b.md」的是提示文字與文件。

## 開放問題

- 先交 diff 能快多少、抓錯數會不會掉：S4 量過（`docs/measurements/2026-10-23-reviewer-real-sessions.md`「新做法對照」）。抓錯數三組一樣（可計分的 6 個命中各中 3 個）；新做法整發反而慢 1.9–3 倍、貴 2.5–3.6 倍。這次的設計分不出 diff 檔單獨的效果（同時變了四件事）；要分就另加一組「舊派工＋diff 檔」
- 很大的 diff 一次交出去，審查者讀不讀得完：S4 試了 G4 兩發（都因 gate-guard 擋下而作廢，只供參考）。第 1 發 3 個審查者都用 Read 讀到 diff 檔最後一行，第 2 發 4 個都只用 Read 讀前段的 diff。另外 Read 不指定範圍會被靜靜截斷：G3（3024 行、253 KB）不帶 limit 只回到第 544 行（約 47 KB），G2 也有一例停在 643 行。見同一份量測文件
- `general-purpose` 裁決者巢狀派 `subagent_type: code-reviewer` 拿不拿得到結果：已結案，2026-10-24 實測拿得到（見 S3 開工前提）
