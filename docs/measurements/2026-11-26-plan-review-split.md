`skills/plan-review/SKILL.md` 的裁決者範本把「數量你決定，**最少 3 個、沒有上限**。計畫越大、牽涉越廣就派越多」改成照段落數定人數與方向
（一段：3 個、各一個方向；兩段以上：每段 1 個加 1 個跨段；最少 3、最多 6），【派工】多寫「計畫有幾段」。使用者依 /usage 決定，要「準、明確」；裁決者維持 opus、審查者維持 haiku。
範本會原樣送進裁決者的 prompt，所以 2026-11-15 的實測不算這一版的，補跑一發。

同一天先改過一版「剛好 3 個」（`b78b992`），跑 `P-med-8` 途中使用者改成照段落數定，那一發中途停掉、沒有結果，不算數。

## 方法

照 `2026-11-15-plan-review-pack/CLAUDE.md`「跑一發的順序」，素材、快照、父 session 都是那一份（2026-11-14 的計畫與事實、快照 `b1935bb`），
只有 `fill.py make … pack` 讀到的是這次改過的 SKILL.md。發代號 `P-med-9`，工作目錄在 scratchpad、新開的。
素材的計畫有進度表、兩段（S1、S2），照新規則應派 3 個：只查 S1、只查 S2、跨段。

## 判準（跑之前寫死）

- **① 派工**：裁決者第一批派出的審查者剛好 3 個（數 prompt 開頭是「你是計畫審查者輪1-R」、代號不帶 `b` 的 Agent 呼叫），
  方向分別是只查 S1、只查 S2、跨段（讀這 3 個 Agent 呼叫的 prompt 人工判）；報告的【派工】寫計畫有 2 段
- **② 讀完**：`readcheck.py` 對這一發 exit 0
- **③ 命中**：那條重大（M1，定義照 `2026-11-15-reviewer-effort.md`「正確答案」）出現在審查者報告的聯集裡；人工判，附報告檔與行號
- **④ 結論合法**：裁決報告有【結論】，值是 `通過`／`不通過（N 條重大）`／`無法判定（…）` 其中之一
- 作廢：`stats.py` 的 errors 不是空的，或洩題檢查有 subagent 讀到暫存區裡講到 M1 的舊報告
- 四條都過 → 採用。任何一條沒過 → 不自己補跑，停下回報，由使用者決定（還原或再跑）
- 預算：只跑這一發（使用者同意約 3 美元；`run.sh` 的上限是 8 美元）

## 補充：人數分支的乾跑（P-med-9 開跑之後、乾跑之前寫的）

`P-med-9` 的素材只有兩段，2 + 1 = 3，量不到「段多就多派」與上限 6。補三個乾跑臂：opus 的 general-purpose subagent 讀一份裁決者指示
（從這次的 SKILL.md 範本填出，計畫是造的：1 段無進度表、5 段、8 段有進度表），不派 agent，只交回段落數與它會派的「代號｜方向」。
乾跑只量「讀完指示會怎麼分派」，不證明真跑時照做。

- 1 段：段落數 1；剛好 3 個，方向是前提、同步點、範圍與驗證各一
- 5 段：段落數 5；剛好 6 個，S1–S5 各一個「只查」加一個跨段
- 8 段：段落數 8；剛好 6 個，一個跨段，其餘 5 個把 S1–S8 分完（每段恰好被一個審查者查、併在一起的是相鄰段）
- 三臂都對才算過；沒過就停下回報，不自己改範本重跑
