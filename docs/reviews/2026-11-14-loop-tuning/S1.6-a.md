## 發現

S1.6-a 的審查結果：④ 寫的計數我重算後完全一樣，但比對方法有三個洞。最大的一個：舊寫法那組裡唯一「對不到」的一段，其實是比對方法誤判，agent 引的原句沒有錯。

Critical 0 / Important 3 / Smells 0 —— 範圍是 097272b 到工作目錄（diff.txt 的 ①–④）

[Important] docs/designs/2026-11-14-loop-tuning-design.md:140 「一個 7 段裡 6 段對得到、1 段對不到」這句是比對方法造成的誤判
  證據：DR1 第 1 條引的是「**原生優先（Claude Code ≥ 2.1.198）**：…CLI `--worktree` 與 subagent `isolation: worktree` 已涵蓋…」，原檔這段跨兩行，而且是 blockquote（`skills/worktree-manager/SKILL.md` 第 9、10 行都以 `> ` 開頭）。④ 的比對只去掉空白，原檔剩下「與>subagent」，於是判成對不到。agent 引的字其實一字不差，只是沒帶換行處的 `>`。我自己重跑（chk.py）結果是 exact=False、ns=False，原因就是這個 `>`。
  失敗情境：舊寫法其實是一臂 7/7 全對、一臂 3 段用了省略號，不是「兩臂都有對不到」。讀紀錄的人會以為不寫明時 agent 連沒用省略號的引文也會改字。這個方法以後拿去比 blockquote、表格或清單裡跨行的引文，都會把對的判成錯。

[Important] docs/designs/2026-11-14-loop-tuning-design.md:140 「3 段用了省略號（切開後每一截都對得到）」把一段順序對調的拼接記成了沒問題
  證據：DR2 第 4 條引的是「**`git stash -u` 在沒東西可存時 exit 0**…真正讓整條鏈靜靜變綠的是這一半」，但 `skills/verification-gate/SKILL.md:41` 原文的順序是「真正讓整條鏈靜靜變綠的是這一半：**`git stash -u` 在沒東西可存時 exit 0**」。前後兩截被對調了，每一截單獨查都是原檔的子字串。
  失敗情境：用「按省略號切開、逐截查子字串」來驗，順序對調和兩處併成一句都會被判成對得到。這正是新規則要擋的「不把兩處併成一句」，現在的驗法抓不到。DR2 回報的那條「矛盾」，正是建在這段對調過的引文上。

[Important] docs/designs/2026-11-14-loop-tuning-design.md:107 寫的通過條件比 ④ 實際查的範圍寬
  證據：第 107 行寫「交回裡「」引的每一段，去掉換行與空白後都對得回原檔」，但 ④ 只取「每條開頭」的「」。DR4 是新寫法那組，它說明欄裡有兩處「feature-x」，`grep -c feature-x skills/worktree-manager/SKILL.md` 回 0。DR3 說明欄裡的「重現原始問題步驟」也沒被查到（剛好在原檔裡）。
